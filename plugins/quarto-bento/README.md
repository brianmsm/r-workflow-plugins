# Quarto-Bento Agent Plugin

A portable companion for agents using **Quarto-Bento**: QMD authoring/computation, retained visual design, structured `qbento` operations, selective source synchronization and conservative recovery.

**Agent plugin manifest version:** `0.1.1`, independently tagged as `quarto-bento-v0.1.1`; consumers receive the revision pinned by their marketplace, not every commit on `main`. This plugin version is **not** the separately published application version: the tested application remains `@brianmsm/quarto-bento 0.1.1` on Linux, JSON agent protocol v1. The plugin does not install or bundle the application, runtimes, assets or fonts.

## Scoped Support and Evidence (0.1.0 Baseline, 0.1.1 Guidance)

The scoped initial release targets **reviewed, trusted local QMD projects on Linux** using the installed `qbento 0.1.1` CLI. Native Codex actor evidence covers saved-design edits, approved selective source synchronization, conservative privacy/recovery stops, ordinary non-Bento negative controls, and one **completed first-render authoring case with a short-header Markdown table**. For executable QMD and public-facing HTML, review all QMD chunks, hooks, inputs, native pending content, and the complete potential HTML visibility before a separately authorized one-shot host render. Source-only `sync --select` never filters retained native HTML content.

This is a deliberately **narrower local acceptance policy** than the earlier strict experimental gate: neither R1-NEW (`NOT_CLEAN`) nor R2-LOCAL (`PASS_LOCAL` under a different protocol) has been reclassified as one of two strict H2 CLEAN rounds. The F02 table/first-render trial passed local S/T/A/H on the earlier correction commit; later editorial instruction changes have **not** been behavior-tested as a new exact-byte candidate. Its `TEXT_MEASUREMENT_UNAVAILABLE` diagnostics mean **visual text fit was not independently measured**. The `0.1.1` **agent-plugin** patch adds optional `quarto-report-design` cooperation and engine-specific guidance for Reveal.js Auto-Animate versus native Bento motion. A synthetic `qbento 0.1.1` experiment confirmed that `auto-animate` does not become a native `morph`, and native `morph` does not sync back to QMD as Auto-Animate; an ordinary same-identity QMD wording edit retained saved native morph without `.qbento-design`. The issue is tracked in [qbento #1](https://github.com/brianmsm/quarto-bento/issues/1). These tests do **not** validate the new skill bytes through fresh native-agent trials or certify cross-format animation fidelity. The native app's backup-only N01 recovery risk remains; do not bootstrap a recoverable project as new. No Windows/macOS, native Claude-agent task execution, unrestricted untrusted QMD execution, complete Studio/browser acceptance, rich/wrapped tables, or cross-machine pixel fidelity is certified. Claude manifest validity is **structural compatibility only**.

## Application 0.2.0 Candidate: Supported Directions (Unreleased)

The **application** `qbento 0.2.0` is a locally reviewed **Linux release candidate**, **not** an npm-published or tagged app yet. Its review tarball (SHA-256 `ae96fc64…`) was created from product HEAD `b52772e` **with uncommitted changes**. It is distinct from both the published app `0.1.1` and this **agent-plugin version `0.1.1`**. Users must check `qbento --version` and choose the intended executable explicitly. Do not replace the global installation merely to try a candidate: invoke an isolated prefix and **copy the entire QMD project including `.qbento/`** for mutation/render tests.

The added guidance is **only for verified app `0.2.0` candidates**: `design` commands/packages and reusable theme styles, variants and QMD slots; source-code/result columns, multi-result layout and opt-in complete-output scrolling; bounded 2D/3D Plotly interaction offline with static SVG/PNG fallback, **Save view** for a 3D camera, and matching-generation native capture. PDF uses complete-output continuations and checked print output, not a new generic `qbento pdf` command. Generated results and widget cameras remain distinct from authorized source edits. For code backgrounds use cards; a code role style alone changes typography/color, not its own panel fill.

The source/behavior contracts are summarized in the existing [authoring](skills/quarto-bento-workflow/references/authoring-components.md) and [sync/output](skills/quarto-bento-workflow/references/sync-and-recovery.md) references; no new skill or runtime dependency is introduced. The product's Linux suite reports 705 passing tests plus four steps, zero failures, one optional omitted comparison; a separate **isolated tarball smoke** verified two real QMD renders and **43/43** structural/content checks. The synthetic smoke did not re-run real mouse/3D-camera or fresh-agent behavior experiments. The product candidate must be retested and its documentation pinned to an **immutable clean release** before advertising general 0.2 compatibility.

## Use and Local Development

With the skill available to the agent, a request can be as simple as:

> Use Quarto-Bento to update this presentation while preserving its design and pending edits.

Codex can explicitly invoke `$quarto-bento-workflow`; optional `agents/openai.yaml` describes that interface. Substantive instructions are shared with other agents, and do not require a particular MCP server or terminal manager. Automatic selection must be tested, not assumed. **Retained design changes are complete only when a fresh `qbento get` confirms the saved fields; editing generated `.bento.html` is not persistent design work.** Selected source sync must separately authorize optional `.qbento-design` annotations, even when the semantic pending ID is approved. **Selected QMD synchronization is not selective HTML publication:** the saved native deck may still contain excluded authored drafts that appear in rendered output. Review the full saved/pending content against the user's publication permissions **before** approving any render; preserve and stop if private material would be exposed. On a known browser-incompatible Codex sandbox, a trusted, explicitly authorized host-render handoff can publish the deck without granting the whole agent unrestricted permissions; this is a **separate operator action**, not a built-in plugin renderer. See [sync and recovery](skills/quarto-bento-workflow/references/sync-and-recovery.md).

For testing **unpublished local changes**, use a separate development marketplace pointing at this plugin directory and consult the [repository setup guide](https://github.com/brianmsm/r-workflow-plugins/blob/feeaf6c71b70a1f5cac46b5f723d3ba613ac32e0/docs/agent-setup.md). The public marketplaces install the version pinned to their release tag, not automatically the local `main`. Claude Code can also load the local directory through `claude --plugin-dir ./plugins/quarto-bento`; manifest validity does not establish native Claude-agent behavior.

The application itself must be available as `qbento`, a portable launcher, or a compatible source checkout. The skill detects which is available; no absolute developer path is embedded. App installation, changes to project configuration, commits and publication remain separately authorized operations.

## Composition, Not Duplication

`quarto-publishing` retains generic authoring, narrative, performance, format configuration and rendering expertise. `r-analytic-core` retains research R coding conventions. They are useful optional companions; this plugin owns only the Bento-specific identity/state/CLI/codec/recovery contract, which stays in force when another capability is consulted. Do not import revealjs styling assumptions into Bento or duplicate existing skills under new names.

Read [architecture](docs/architecture.md), [roadmap](docs/roadmap.md), [validation cases](docs/validation-cases.md) and [initial findings](docs/pilot-findings.md). Raw local tests belong outside the distributable plugin; any validation summary must distinguish application tests, agent behavior, source integrity, rendered output and visual/UI evidence.
