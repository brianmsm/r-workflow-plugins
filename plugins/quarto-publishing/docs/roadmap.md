# Quarto Publishing Plugin Roadmap

## Purpose of This Roadmap

This roadmap defines the staged implementation plan for the `quarto-publishing` plugin.

It should be read together with:

[`architecture.md`](architecture.md)

The architecture document describes the mature target design of the plugin. This roadmap describes how to reach that target gradually, starting with a useful first version, testing it on real Quarto projects, correcting its behavior, and then expanding or splitting skills as justified by actual usage.

The roadmap should not replace the architecture document. Instead, it operationalizes it.

## General Development Strategy

The plugin should be developed through repeated cycles:

1. Implement a small but functional version.
2. Test it with real Quarto projects.
3. Record failures, ambiguities, over-triggering, under-triggering, missing guidance, and confusing boundaries.
4. Correct the existing skills before adding many new ones.
5. Split references into independent skills only when real use shows that they deserve independent activation.
6. Expand toward the target architecture described in `architecture.md`.

The initial goal is not to implement the full target architecture. The initial goal is to create a reliable, useful plugin that can support common Quarto authoring, configuration, reporting, performance, and troubleshooting tasks.

## Target Mature Architecture

The mature architecture is defined in `architecture.md` and includes the following skills:

1. `quarto-authoring-core`
2. `quarto-project-configuration`
3. `quarto-format-configuration`
4. `quarto-multiformat-compatibility`
5. `quarto-report-design`
6. `quarto-computation-performance`
7. `quarto-rmarkdown-migration`
8. `quarto-publishing-deployment`
9. `quarto-accessibility-quality`
10. `quarto-render-troubleshooting`

This roadmap assumes that not all of these skills must exist as independent skills in the first release.

Some final skills may initially live as references inside broader skills. They should be split later only when their activation patterns become clear.

## Roadmap Principles

The roadmap follows these principles:

* Prefer useful implementation over complete theoretical coverage.
* Start with skills that are most likely to be used in real Quarto workflows.
* Avoid creating too many small skills before observing how agents actually use the plugin.
* Keep `SKILL.md` files concise and operational.
* Put detailed technical guidance in `references/`.
* Avoid scripts unless the task is deterministic, repeatable, and useful.
* Avoid assets until reusable templates or skeletons are actually needed.
* Treat real project testing as part of plugin design, not as a final afterthought.
* Correct unclear skill boundaries before adding new features.
* Do not claim that a render or output has been verified unless the agent actually performed the verification.

Create the minimal plugin structure and documentation needed to start development.

Create:

* `plugins/quarto-publishing/.codex-plugin/plugin.json`

The initial `plugin.json` should be clean and should not keep unused placeholders generated by scaffold scripts.

### Expected Outcome

The plugin exists as an installable unit inside the monorepo, even if only a subset of skills has been implemented.

### Validation

Check that:

* The plugin name is stable: `quarto-publishing`.
* The plugin version remains `0.0.0` during scaffold-only development.

* The plugin version changes to `0.1.0` only in the first usable release commit.
* The plugin manifest points to `./skills/`.
* The README explains the plugin purpose without duplicating the full architecture.
* The roadmap references `architecture.md` as the target design.

## Phase 1: First Functional Version, `v0.1.0`

### Goal

Create a first functional version that can be tested on real Quarto projects.

This version should support the most common and high-value tasks:

* Writing and reviewing `.qmd` content.
* Configuring common output formats.
* Managing basic project configuration.
* Designing report structures.
* Handling expensive renders.
* Diagnosing common render failures.

### Initial Skills

Implement these skills as independent skills in `v0.1.0`:

1. `quarto-authoring-core`
2. `quarto-project-configuration`
3. `quarto-format-configuration`
4. `quarto-report-design`
5. `quarto-computation-performance`
6. `quarto-render-troubleshooting`

These six skills provide enough coverage for real use while avoiding excessive fragmentation.

The initial scaffold `quarto-publishing-workflow` skill was removed before `v0.1.0`. Its broad workflow guidance was superseded by the six Phase 1 skills, which provide clearer activation boundaries.

### Topics Temporarily Folded into Other Skills

The target architecture includes additional skills that may not exist yet in `v0.1.0`.

In the first version, they can be folded as references:

* `quarto-multiformat-compatibility` can initially live inside `quarto-format-configuration/references/`.
* `quarto-rmarkdown-migration` can initially live inside `quarto-authoring-core/references/` or `quarto-project-configuration/references/`.
* `quarto-publishing-deployment` can initially remain deferred, with only minimal cross-references from `quarto-project-configuration` when output directories or resources affect later publishing.
* `quarto-accessibility-quality` can initially live inside `quarto-report-design/references/` and `quarto-render-troubleshooting/references/`.

This is a temporary implementation strategy. The target architecture still treats them as future independent skills.

### Minimal Skill Structure

Each skill should start with:

* `SKILL.md`
* `agents/openai.yaml`
* `references/` only when needed

Avoid creating `scripts/` and `assets/` in `v0.1.0` unless there is a concrete and immediate use case.

### Initial Reference Priorities

For `quarto-authoring-core`:

* `qmd-authoring-patterns.md`

This compact reference initially covers document YAML, executable cells, cell or chunk options, figures, tables, cross-references, citations, callouts, light adaptation of R Markdown idioms inside `.qmd` files, and engine-aware notes for R/knitr, Python/Jupyter, Julia, or prose-only documents. More focused references can be split later if real usage shows they are needed.

For `quarto-project-configuration`:

* `quarto-project-configuration.md`

This compact reference initially covers `_quarto.yml`, `_metadata.yml`, project/document metadata placement, profiles, parameters, render targets, output directories, resources, project-level `freeze`, and the boundary with format configuration.

For `quarto-format-configuration`:

* `quarto-format-configuration.md`

This compact reference initially covers format choice, YAML shape patterns, HTML, PDF via LaTeX, PDF via Typst, DOCX, revealjs, PowerPoint, Beamer, secondary formats, shallow book/website/manuscript output behavior, custom format cautions, and minimal multiformat notes.

For `quarto-report-design`:

* `executive-report-structure.md`
* `technical-report-structure.md`
* `academic-report-structure.md`
* `accessibility-basic-checklist.md`

For `quarto-computation-performance`:

* `computation-performance.md`

This compact reference initially covers cache/freeze, long-running renders, externalized computation, precomputed artifacts, pipeline escalation, random seeds, proportional validation, and agent behavior when full renders may be expensive.

For `quarto-render-troubleshooting`:

* `render-troubleshooting.md`

This compact reference initially covers render failure triage, diagnostic commands, YAML errors, cell or chunk execution errors, paths and assets, LaTeX and Typst failures, citations, cross-references, HTML verification, local-vs-CI differences, and honest verification claims.

### Expected Outcome

By the end of Phase 1, the plugin should be useful for ordinary Quarto tasks, including:

* Creating or reviewing a `.qmd`.
* Improving cell or chunk options.
* Fixing cross-references.
* Setting up basic `_quarto.yml`.
* Choosing and configuring common output formats.
* Structuring executive or technical reports.
* Reducing render time for heavy documents.
* Diagnosing common render failures.

### Release Criteria for `v0.1.0`

Release `v0.1.0` only when:

* All initial skills have valid `SKILL.md` frontmatter.
* Each skill has a clear activation boundary.
* Each `agents/openai.yaml` is aligned with the corresponding `SKILL.md`.
* The plugin README explains the initial scope.
* The changelog describes the first release.
* The plugin does not contain unused placeholder fields.
* The initial skills pass available validation tools.
* At least a small set of real or realistic Quarto tasks has been tested manually.

## Phase 2: Real Project Testing Cycle

### Goal

Use `v0.1.0` on real projects before expanding the plugin.

This phase is essential. The purpose is to learn whether the initial skills activate correctly, whether their boundaries are clear, and whether important guidance is missing.

### Test Project Types

Test the plugin on several types of Quarto projects:

1. A simple single-file HTML report.
2. A single-file PDF report.
3. A single-file DOCX report.
4. A multi-output report targeting HTML and PDF.
5. A report with tables and figures.
6. A report with citations and cross-references.
7. A report with heavy R computation.
8. A small Quarto website.
9. A slide deck, preferably revealjs.
10. A broken project with render errors.
11. A legacy `.Rmd` file being moved toward Quarto.
12. A report requiring executive and technical versions.

Not all test cases need to be complex. The goal is to expose practical problems.

### What to Observe

For each test, record:

* Which skill was expected to activate.
* Which skill actually activated.
* Whether the selected skill was appropriate.
* Whether another skill should have been selected instead.
* Whether the skill gave too much or too little guidance.
* Whether references were useful.
* Whether a missing reference was needed.
* Whether a future skill should be split earlier than planned.
* Whether a skill is too broad.
* Whether a skill is too narrow.
* Whether the agent overclaimed verification.
* Whether the agent avoided full renders when proportional validation was enough.
* Whether the agent preserved the user’s analytical intent.

### Suggested Testing Log

Maintain a simple testing log, either in `docs/testing-log.md` or as temporary development notes.

Each entry should include:

* Date.
* Project type.
* User task.
* Expected skill.
* Actual skill.
* Result.
* Problem observed.
* Required correction.
* Whether this implies a roadmap change.

### Expected Outcome

At the end of Phase 2, there should be enough evidence to decide whether to:

* Correct skill descriptions.
* Move content between skills.
* Add missing references.
* Split a folded topic into its own skill.
* Delay some planned skills.
* Add deterministic scripts.
* Add reusable assets.

## Phase 3: Correction and Stabilization, `v0.1.x`

### Goal

Improve the first functional version based on real project testing, without expanding the plugin too quickly.

This phase should focus on correction, not feature growth.

### Correction Types

Apply corrections such as:

* Improve skill `description` fields.
* Clarify when each skill should and should not be used.
* Move misplaced guidance from one skill to another.
* Shorten overloaded `SKILL.md` files.
* Move long material into `references/`.
* Add missing checklists to references.
* Fix incorrect Quarto assumptions.
* Improve troubleshooting steps.
* Improve guidance for render verification.
* Add stronger warnings against unverified claims.
* Improve YAML examples only where they are necessary.
* Improve references for common failure modes.

### Do Not Overexpand Yet

During `v0.1.x`, avoid:

* Adding many new skills.
* Adding templates before repeated use justifies them.
* Adding scripts before manual testing proves the need.
* Turning every reference into a skill.
* Trying to cover every Quarto format in depth.

### Expected Outcome

The `v0.1.x` series should make the plugin more reliable and better calibrated.

This stage should produce a stable foundation for expansion.

### Release Criteria for Patch Versions

Use patch releases, such as `v0.1.1` or `v0.1.2`, when changes include:

* Clarified skill descriptions.
* Small reference additions.
* Corrections to guidance.
* Better activation boundaries.
* Better troubleshooting checklists.
* Improved examples.
* Documentation corrections.

Patch versions should not introduce major skill restructuring.

## Phase 4: First Expansion, `v0.2.0`

### Goal

Split the most important folded topics into independent skills if testing shows that they deserve independent activation.

### Candidate New Independent Skills

The strongest candidates for `v0.2.0` are:

1. `quarto-multiformat-compatibility`
2. `quarto-rmarkdown-migration`

`quarto-multiformat-compatibility` should become independent if real testing shows repeated tasks like:

`quarto-rmarkdown-migration` should become independent if real testing shows repeated tasks like:

* “Convert this `.Rmd` to `.qmd`.”
* “Migrate this Bookdown project.”
* “Move Xaringan slides to revealjs.”
* “Convert `_output.yml` to `_quarto.yml`.”

### Implementation Scope

For `quarto-multiformat-compatibility`, create:

* `SKILL.md`
* `agents/openai.yaml`
* references such as:

  * `figures-across-formats.md`

For `quarto-rmarkdown-migration`, create:

* `SKILL.md`

* Remove duplicated content from older references.
* Replace folded references with pointers to the new skills.

* Update testing cases.

### Expected Outcome

By the end of `v0.2.0`, the plugin should better handle multi-output workflows and legacy R Markdown migration.

## Phase 8: Tooling and Reusable Assets, `v0.4.0`

### Goal

Add scripts and assets only after repeated testing shows that they are useful.

This phase should not add scripts or assets just because they are possible.

### Candidate Scripts

Potential scripts:

* Check whether expected rendered files exist.
* Extract output formats from a Quarto YAML file.
* Detect missing bibliography files.
* Detect missing figure or asset files.
* Run targeted `quarto render` commands.
* Summarize render logs.
* Check internal links in generated HTML.
* Detect obvious long-running executable cells or chunks.
* Check for missing alt text in `.qmd` files.
* Validate project structure heuristically.

### Candidate Assets

Potential assets:

* Minimal Quarto report skeleton.
* Executive report skeleton.
* Technical report skeleton.
* Academic manuscript skeleton.
* Multi-format report skeleton.
* Quarto website skeleton.
* Revealjs slide skeleton.
* Reference DOCX template.
* Starter SCSS file.
* Publication checklist template.

### Acceptance Criteria for Scripts

A script should be added only if:

* The task is deterministic.
* The script saves time compared with manual inspection.
* The script is likely to be reused.
* The script does not require fragile assumptions.
* The script produces clear output for an agent.
* The script does not replace necessary judgment.

### Acceptance Criteria for Assets

An asset should be added only if:

* The structure is reused across projects.
* The asset reduces boilerplate.
* The asset is generic enough for the plugin.
* The asset does not impose a narrow style.
* The asset can be documented clearly.
* The asset does not create unnecessary maintenance burden.

### Expected Outcome

By the end of `v0.4.0`, the plugin may include practical helper scripts or reusable templates, but only where justified by real use.

## Versioning Strategy

Use plugin-level semantic versioning.

During scaffold-only development, keep `plugin.json` at `0.0.0` and do not create a public tag. The first usable release changes `plugin.json` to `0.1.0` in the release commit and creates the tag `quarto-publishing-v0.1.0`.

After a release, keep `plugin.json` at the latest released version while normal development continues. Track work for the next release under `## [Unreleased]` in `CHANGELOG.md`. When the next release is ready, update `plugin.json` in the release commit and create the corresponding plugin tag.

### Patch Versions

Use patch versions for:

* Corrections.
* Clarifications.
* Small reference improvements.
* Better examples.
* Minor metadata changes.
* Small troubleshooting improvements.

Example:

`quarto-publishing-v0.1.1`

### Minor Versions

Use minor versions for:

* New skills.
* New references with substantial scope.
* New scripts.
* New assets.
* Significant expansion of supported workflows.
* Refactoring folded topics into independent skills.

Example:

`quarto-publishing-v0.2.0`

### Major Versions

Use major versions for:

* Breaking skill names.
* Removing or renaming skills.
* Major activation boundary changes.
* Large structural changes.
* Incompatible plugin manifest changes.

Example:

`quarto-publishing-v1.0.0`

## Testing Strategy

Testing should be practical and project-based.

The plugin should be tested with real or realistic Quarto projects, not only with isolated examples.

### Minimum Test Scenarios

For each release cycle, test at least some of the following:

* Single `.qmd` HTML report.
* Single `.qmd` PDF report.
* Single `.qmd` DOCX report.
* Multi-format HTML and PDF report.
* Report with citations and bibliography.
* Report with cross-references.
* Report with `gt`, `flextable`, `kableExtra`, or similar table tools.
* Report with interactive HTML widgets.
* Quarto website.
* Quarto revealjs presentation.
* Long-running render.
* Broken render.
* Legacy `.Rmd` migration.
* Executive report structure.
* Technical report structure.
* Deployment scenario.
* Accessibility review.

### Evaluation Questions

For each test, ask:

* Did the right skill activate?
* Did the skill avoid unnecessary complexity?
* Did the agent preserve the user’s intent?
* Did the agent distinguish authoring, format configuration, project configuration, and troubleshooting?
* Did the agent avoid overclaiming render verification?
* Did the agent recommend proportional validation?
* Did the agent recognize when a full render was unnecessary?
* Did the agent correctly identify format-specific limitations?
* Did the agent handle multi-format issues appropriately?
* Did the agent provide useful next steps when tools were unavailable?

## Correction Strategy

Corrections should be prioritized in this order:

1. Incorrect or unsafe guidance.
2. Overclaiming render or output verification.
3. Wrong skill activation.
4. Missing troubleshooting steps.
5. Confusing skill boundaries.
6. Missing references for common real tasks.
7. Overly long `SKILL.md` files.
8. Duplicated guidance across skills.
9. Missing examples.
10. Nice-to-have expansions.

Correction should come before expansion.

## Criteria for Splitting a Reference into a Skill

A reference should become a standalone skill when:

* Users repeatedly ask for that topic as the main task.
* The parent skill becomes too broad.
* The topic has its own workflow.
* The topic requires its own activation description.
* The topic has distinct failure modes.
* The topic requires several references of its own.
* Keeping it folded causes the agent to select the wrong skill.
* The split would reduce confusion.

Examples:

* `multiformat-notes.md` becomes `quarto-multiformat-compatibility`.
* `rmarkdown-migration.md` becomes `quarto-rmarkdown-migration`.
* `deployment-notes.md` becomes `quarto-publishing-deployment`.
* `accessibility-basic-checklist.md` becomes `quarto-accessibility-quality`.

## Criteria for Keeping a Topic as a Reference

A topic should remain a reference when:

* It is usually auxiliary.
* It does not have a clear activation pattern.
* It is only needed inside a larger workflow.
* It is too narrow to justify a skill.
* Splitting it would create unnecessary fragmentation.
* It mainly provides examples, checklists, or technical details.

Examples:

* Cross-references.
* Citations.
* Chunk options.
* YAML patterns.
* HTML theming.
* LaTeX options.
* Typst notes.
* Callouts and divs.
* Tables across formats.
* Screenshot review.
* Link checking.

These may later become skills, but only if real usage justifies the split.

## Final Roadmap Summary

The plugin should evolve in four broad movements:

1. Build a first functional version with the most useful core skills.
2. Test it on real Quarto projects and correct boundaries, references, and behavior.
3. Split folded topics into independent skills only when real use justifies it.
4. Add deployment, accessibility, scripts, assets, and advanced specializations gradually.

The mature target remains the architecture defined in:

[`architecture.md`](architecture.md)

The roadmap should remain flexible. If real testing shows that a future skill is needed earlier, it can move forward. If a planned skill does not show a clear activation pattern, it should remain a reference until there is a stronger reason to split it.
